# Charity Impact Reports preliminary reviews

The public landing page leads to the existing account-gated /charity-impact-reports/review/. Existing human-review uploads remain at /charity-impact-reports/review/human/.

The authenticated API uses the existing platform identity and same-origin checks. It takes the confirmed charity from the onboarding profile, reuses published document discoveries and checks a maximum of three official website pages. Only observed public HTTPS PDF links are offered; dedicated impact reports are retained alongside annual reports. Dates are displayed only when the existing candidate identifies a reporting period. Failed discovery says the document could not be found, not that no report exists.

Users explicitly confirm a document before requesting either framework. Uploads are PDF-signature checked and capped at 4 MB. Public retrieval uses the existing DNS-pinned, public-address-only PDF fetcher and robots policy. Private records are scoped to the account, or to a matching authorised charity owner/admin workspace. Founder activity uses the existing verified founder permission. The legacy account service remains unchanged.

The additive migration creates three tables in the existing research console database. It does not change any account, customer or assessment tables. Reviews are queued durably, leased for four minutes, and resumed by account polling or the existing charity-preparation cron. The existing cron runs daily, so an interrupted job may resume only on a later visit or that scheduled run. One job runs per invocation. Claims and Excellence processing for the same document are serialised with a transaction advisory lock. Attempts are capped at three; completed versioned results are reused.

The unpdf package extracts physical PDF pages once. Reports with less than 300 readable characters, substantial unreadable pages, more than 200 pages or over 180,000 characters are rejected with an upload/help alternative. OCR is not implemented. AI uses the existing server-side OpenAI connection and Responses structured outputs, with storage disabled. Report text is untrusted data. Every emitted quotation is checked against the claimed page using Unicode and whitespace normalisation. Invalid citations or malformed results fail rather than being published.

Claims Code definitions come from the existing SORP introduction. The five 0–4 disclosure ratings map to 25-point principle bands. The overall equal-weight score is rounded to the nearest five, only if all principles have sufficient evidence. Missing disclosure and uncertainty are not zero scores. Excellence uses the existing five-pillar questions as its definitions; all numerical ratings are removed and no organisational maturity score is produced. Published-report review is not the full diagnostic, certification or assurance.

Commercial requests use the existing continuous-improvement contact endpoint and Founder Enquiries. Meeting booking uses the existing free calendar component. No email or calendar write is performed automatically by discovery or review. Real booking sends its normal invitation only after the visitor confirms it.

Validation performed: production build/typecheck, lint (two existing warnings), 294 unit tests, two PDF extraction tests, desktop and 390px browser contracts with controlled responses, and validation-database runtime-role scope checks. Browser fixtures are explicitly synthetic; these checks do not prove real model findings, real document discovery, authenticated return sessions, or calendar invitation delivery. Those require live end-to-end validation before describing the MVP as fully verified.
