# Private accountant research console

The console is part of the existing SORP2026 Next.js application at `/console/`. It reuses the SORP account service; each private page and API request verifies the backend session and checks its email against server-only `ADMIN_EMAIL`. The founder dashboard link is based on the same server check. No client-side email allowlist or test bypass is shipped. ChatGPT sign-in is not configured for this deployment. The public directory and other products are unchanged.

## Data and environments

Production uses the existing Neon `social-impact-excellence-platform` project (`lucky-sky-23094766`), main branch (`br-dark-block-audwtcnr`), with a separate `research_console` schema. Preview testing uses `sorp-console-validation` (`br-calm-queen-aucbc1bk`). Production and preview use different secrets and a `sorp_console_runtime` role restricted to the console schema. Its lack of access to `public.users` and lack of elevated role membership were checked. `CONSOLE_DATABASE_URL` is stored as a Vercel secret; `ADMIN_EMAIL` is server-only. No production secrets are committed or copied to client bundles.

The additive, repeatable migrations are `migrations/001_research_console.sql`, `002_console_completion.sql` and `003_icaew_benchmark.sql`. For the existing runtime role, grant SELECT/INSERT on benchmarks and backup_runs, UPDATE on backup_runs, and UPDATE(address) on offices after migration 002. Raw evidence, research runs, examined/unavailable sources, assessments, methodology revisions, reviews, import archives and change history are separate tables. Scores and original methodology references are append-only to the runtime role. Every change of thresholds creates a retained version. Displayed evidence levels use the latest boundaries; history shows the original version and level.

`node scripts/console-seed.mjs` emits reviewable SQL preserving the existing 110-row import, the separately researched Burton Sweet record, and three previously absent requested candidate names. It creates 114 unreviewed candidates, no invented scores and no completed research. Offices do not create firm records. Prior source classifications are preserved as provenance, not promoted to completed console assessments. The supplied ten-firm pilot has now been imported: ten original v1.0 assessments, 39 evidence records, original research dates, levels and verbatim workbook methodology. The 110-row directory was matched against existing records and supplemented missing information without replacing manual research. All 115 existing office records were retained.

## Research behaviour and limits

A name or website is first matched against existing names, aliases and domains. Confirmed website research works without a search-provider credential. Unknown-name discovery uses the deployed Brave provider when server-only `BRAVE_SEARCH_API_KEY` is configured; it is currently missing. Search candidates require confirmation of the official identity. The collector follows the homepage and up to eleven relevant same-site HTML links to depth two, prioritising charity and SORP pages, plus a supplied ICAEW record. It checks robots policy, pins public DNS addresses, validates redirects, limits bytes/time and records inaccessible sources. PDF, JavaScript-only and blocked sources require manual review. No development-only search tool is represented as a deployed feature.

The versioned v1.1 rubric contains Marcus's twenty explicit criteria across the five fixed category maxima. A conservative deterministic evaluator awards each criterion once, retains the exact source passage (or labels an imported research paraphrase), URL, evidence ID, points, reason and confidence, and prevents the same training/publication fact earning overlapping awards. Generic directory membership and general qualifications do not earn points. Failed or insufficient research remains unscored; zero is only assigned after sufficient source coverage. Each result is provisional until reviewed. False negatives are possible: human corrections require a reason and retained evidence. Changing points or enabled criteria creates a new methodology version. Pilot calibration is separate from current firm assessments and never replaces original v1.0 scores.

The dashboard shows ICAEW's published **12,000+ firms** benchmark, from https://www.icaew.com/about-icaew/find-a-chartered-accountant (accessed 12 October 2026). This is an approximate published directory figure, not an exact UK-only unique-firm denominator. The latter remains pending an authorised complete export with stable firm identifiers, UK scope and branch/trading-name reconciliation. Progress displays absolute counts and milestones, not a fabricated population percentage.

## Imports, exports and recovery

CSV/XLSX uploads support preview, candidate validation, possible-duplicate warnings, preservation of all workbook cells/sheets in the import archive and idempotent reimports. Existing records are not overwritten or automatically merged. Recognised pilot and directory workbooks use a namespace-aware XLSX parser and transactionally import mapped fields; all unstructured original cells remain recoverable. Historical scores are validated against category caps and totals. Imports are previewed before confirmation; exact reimports are idempotent. Manual confirmed merges retain the source firm identity and a recoverable change trail.

XLSX exports include firms, people, offices, evidence, runs, source attempts, assessments, reviews, history and methodologies. CSV exports firms. Formula-leading text is neutralised. Exports can be restricted to approved firms. Server-side filtering/search/pagination limits ordinary lists to 25 firms. Workbook uploads are limited to 3 MB, 5,000 rows and 20 MB declared uncompressed ZIP data; exports currently cap at 10,000 firms.

Neon's observed point-in-time history window is six hours, not an unlimited backup promise. A pre-migration snapshot `snap-green-paper-aul38km7` was created on 12 October 2026, expiring 19 October 2026. Before future migrations, create a fresh snapshot and test on a branch. For a consistent portable backup, run `node scripts/console-backup.mjs /private/location/backup.json` with `CONSOLE_DATABASE_URL` set. This uses a repeatable-read transaction and writes all console tables, including import archives, with mode 0600 and no overwriting. Store that file outside the deployment filesystem. A test backup was verified locally. Daily backups run at 06:00 UTC via the bearer-protected Vercel cron endpoint. Every console table is read in one repeatable-read transaction, compressed, encrypted with AES-256-GCM and written to the private `sorp-console-backups` bucket in the existing Neon project. Each upload is downloaded, decrypted and SHA-256 checked. The first backup and at least weekly thereafter restore all values into `console_backup_restore` on the isolated `sorp-console-recovery-tests` branch (`br-quiet-sunset-auboqwdc`), checking exact row contents and foreign-key relationships. Thirty-day retention only activates after successful restore verification. Failure or stale backup alerts appear in the private console; Vercel job errors are logged. This is separate from the database and deployment filesystem, but shares the Neon provider/account failure domain. A one-click production restore is deliberately not exposed. For recovery, restore into an isolated Neon branch, verify row counts, source relationships, assessments and access checks, then repoint only `CONSOLE_DATABASE_URL`; never restore unrelated MSI tables over production.

Backup configuration is server-only: `CONSOLE_BACKUP_BUCKET`, `CONSOLE_BACKUP_ENDPOINT`, `CONSOLE_BACKUP_ACCESS_KEY_ID`, `CONSOLE_BACKUP_SECRET_ACCESS_KEY`, `CONSOLE_BACKUP_ENCRYPTION_KEY`, `CONSOLE_BACKUP_RESTORE_DATABASE_URL` and `CRON_SECRET`. Preview uses `CONSOLE_BACKUP_PREFIX=validation/`; production defaults to `daily/`. Keep the encryption key recoverable: it is stored as an encrypted Vercel project variable for authorised project administrators. Do not rotate it without retaining old keys for old backups. The storage credential is scoped to storage read/write. To recover a downloaded encrypted object, use `decryptBackup` from `backup-crypto.ts` with the matching key, then restore its `tables` using `scripts/console-restore.mjs` into a fresh isolated database and verify before changing the application connection. Complete plaintext JSON and spreadsheet exports are also available only inside the authenticated console.

## Verification

The release passed 55 console flow checks, including desktop/mobile accessibility, plus the existing public homepage and account/product tests. Review-page real owner sign-in remains a user check; no password was requested.

- `npm run build`, `npm run typecheck`, `npm run lint` (one pre-existing warning in public/design-preview/accountants-advisers/preview.js).
- `npm run test:product-unit` checks existing product behaviour.
- `node --experimental-strip-types --test tests/product-unit/console-security.test.mjs` checks private-network rejection, URL restrictions and scoring boundaries.
- `tests/console-flow.mjs` exercises actual API routes and Postgres plus desktop/mobile browser flows. It uses a disposable PostgreSQL container on loopback port 5433 and explicitly resets **only that local QA schema**. `tests/console-auth-fixture.mjs` is a local stand-in for the trusted account backend; no application auth bypass exists. Run the app with `ADMIN_EMAIL=owner@example.invalid`, `SORP_BACKEND_ORIGIN=http://127.0.0.1:4319`, and the local QA database URL. These fixture identities and research records never enter production.
- `NODE_OPTIONS=--conditions=react-server npx tsx scripts/console-verify-completion.ts` is an explicit release check on Vercel: initialise v1.1, calibrate the ten pilot records when present, collect real Burton Sweet sources, require a source-linked provisional assessment, then upload/download and verify the encrypted backup. It is not part of the ordinary build command.

The owner must use their existing SORP password to complete a live authenticated browser session; the release agent does not have or change that password. Logged-out deployed routes and data-denial checks are verified independently. The console's “What's working?” page distinguishes working flows, missing configuration, future features and connection failures.
